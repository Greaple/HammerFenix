## Engine

- Blend modes (2C.6): `swf-types` numbers them from 0 (Normal 0, Layer 1, Multiply 2, Screen 3, Add 7, Overlay 12), one less than the SWF's byte; the port used to read them as SWF bytes, so the timelines' 30 Adds (portals, sphinx and sarcophagus lights, death FX) and 73 Overlays (bombs, torches, flames, explosions) drew as normal. Add, multiply and screen are Pixi's. `OVERLAY` is `OverlayFilter`, a filter that reads the backdrop (the renderer has `useBackBuffer`); it draws at the resolution of its target, as Pixi's filters default to resolution 1 and the backdrop copy then did not line up (the shifted, banded zone of 2B.4). Used by the timelines, the explosions (`FxManager.attachExplosion`) and the map's pit. Timeline `LAYER` (the HUD's life icon, two loader clips) is an alpha filter; from code it is `SwfMovieClip.setLayerBlend` (the darkness), whose `ERASE` holes are Pixi's `erase`. No timeline uses the other modes.
- Filters (2C.6): timeline filters (`PlaceObject3`) are built and drawn: 19 glows (Framboise's outline, the pause screen's titles, the sarcophagus and sphinx, tiles) and 33 color matrices (the silver coin, the enemy statuettes of `hammer_item_score` 179 to 185, tiles, the player). Flash draws a filtered clip as a bitmap, then its color transform and blend: the slot's filter list keeps that order; a pure alpha change stays `alpha`. `GlowFilter` takes Flash's quality (1 box, 2 a tent twice as wide); `BoxBlurFilter` is Flash's `BlurFilter` (one box pass per axis), for item 84's clouds and the level fade. Code glows: `FxManager.addGlow` (strength 100: an outline) on the HUD's level and score, the level name, score pops, key messages and the soccer ball; Bat, Framboise and item 86 set theirs. SWF text fields no longer have the drop shadow they had from the start (Flash text has none). HUD and pause screen compared in Ruffle.
- Color transforms: a timeline update with an identity color transform resets the previous one (the end of a fade); the build used to drop it, so fades froze one step short (the darkness veil at 79%, the message panel, the pointer, the lives, 24 clips in all). `tools/build-swf.ts` keeps it on updates, as it does for matrices (2B.4).
- SWF frame scripts: all 89 run in `src/engine/swf/Avm1.ts`, with function definitions (`DefineFunction`, `DefineFunction2`: registers, locals, preloads), `Return` and `duplicateMovieClip` (2C.6): the particle emitters of the accessories and the sphinx (`_gfx` #234, `_anims` #150: 16 light strands, as the loop is `i <= max`) and the ghosts of item 86's background (`_anims` #3200). Tested in `tests/avm1.test.ts`. The site's intro (3.5) added arrays and objects (`InitArray`, `InitObject`), `GetURL2`, `Key.isDown`, `attachMovie` (also called bare, as a method of the timeline), the `_root` preload, and UTF-8 strings (every SWF of the game is version 7 or 8); `Key` and `getURL` go through `setAvm1Host`. Two Flash rules came with it, for scripts only (the port's own code sets fields directly): a clip a script moved, scaled, turned or faded is no longer placed by its parent's timeline (Ruffle's `transformed_by_script`: matrix, color, blend and filters), and `_xscale`, `_yscale` and `_rotation` are Flash's own view of the matrix (Ruffle's `cache_scale_rotation`: read from it as scale, rotation and skew, kept as a script set them, `_rotation` between -180 and 180), so a clip its timeline flipped reads a positive `_xscale` and a `_rotation` of 180 (the intro's second banana, 2026-11-13: it went round a full turn). The intro also plays its frames as Flash does (`stepMovie`, Ruffle's AVM1 `run_frame`): every clip advances, then the frame scripts run, the newest clip's first, so a child's runs before its parent's (its bananas fight once more before the knockout); the game's clips still run their scripts as they advance, parents first. No replay changed. Not ported: Flash keeps `_x` in twips and `_alpha` in 1/256 steps, so a script's small steps round (the intro's fades of 1.3 % a frame advance by 1.17 %); the port keeps the exact values.
- Frame scripts of a frame reached by `gotoAndStop`, `nextFrame` or `prevFrame` from game code are queued and run after the logic tick or animation step (`runQueuedFrameActions`), as Flash runs them once the running script ends. This lets FX stepped by `Animation.update` loop from their own label (the shield, `hammer_fx_exit`, `hammer_fx_pointer`) and FX that end in `removeMovieClip` remove themselves. `gotoAndPlay` and AVM1 gotos still run them at once.
- Backward timeline seeks keep children that stay on the same depth, as Flash does.
- Text fields bound to a variable (`DefineEditText` `variableName`, e.g. `label`, `_parent.label`) show it: `SwfMovieClip.setVariable` (the original's `mc.label = ...`) updates them, and a field placed later reads it (3.4). HTML fields start with their text, not their markup. HTML text keeps `<b>`, `<font color>` and `<br>` (Pixi tag styles, `parseFlashHtml`); other tags are dropped (2B.4).
- `_width` / `_height` are the exact vector bounds, hidden children included, as in Flash. Hit boxes no longer include the 1 px rasterization margin.
- Animation runs at 40 Hz, tied to the 32 Hz logic (5 steps per 4 ticks).
- Input is sampled once per tick (`InputController.poll`), and can be recorded and replayed (`InputRecording.ts`). `SwfLibrary.headless()` runs the game in Node.
- One input per player (G.2): `poll` makes one action mask per player. Each player has their own keys (`PlayerKeys`, as Flash key codes), set by `PlayerEntity.ctrl` (`PlayerController.setKeys`, `setAlt`, ported for the modes of Phase 4), and their own key locks; `GameMode.insertPlayer` gives the pids and the number of players, and a new game puts every player back on the default keys. The default keys are the original's (arrows, Space, Ctrl as `setAlt`) plus the port's W A S D / Z Q S D and X or J for the bomb. The game's keys (pause, music, give-up, disguise, map, sound) and player 1's touch buttons go in player 1's mask, from every device. A letter key counts as the letter of the keyboard layout (`KeyboardEvent.key`), as Flash's key codes did, since the modes chose their letters for AZERTY (`TimeAttackMulti`'s Z Q S D and A); a key with no Latin letter counts by its QWERTY place. Controllers go to players in connection order; extra ones wait, and take the place of a player's controller that is unplugged. Recordings keep player 1's masks in `input`, so solo replays are unchanged, and the other players' in `otherInputs`. The menus read the default keys and every player's controller. Deviation: the original reads a key's alternative only through `keyIsDown`; here it counts everywhere (only the bomb key has one). Tested in `tests/players.test.ts`, with a two-player game recorded and replayed headless.
- Controllers (G.1, port addition: the Flash game had the keyboard only): `src/engine/Gamepad.ts` reads each player's controller (player 1's is the first one connected; see G.2 above), with the standard mapping: D-pad and left stick move (dead zone with hysteresis, up asks a firmer push), A or up jumps, B, X or the right trigger (R2) drops a bomb, Start pauses, Back / Select switches the music, Y changes the disguise (2C.3), L1 (LB, L) shows the world map (2C.4). It goes through the same action mask as the keyboard, so recordings work. Menus read their own moves (`InputController.consumeMenu`): the D-pad or stick, A or Start confirm, B goes back; the keyboard keeps arrows, the bomb key and P / Escape. While a dialog is open the controller's presses close it (A, B, Start) or scroll it (D-pad), and the game ignores the controller until it is let go. The screens show the buttons of the device used last (`InputController.device`, `html[data-input]`): the menu's action button (keycap, A or B, nothing on touch), the pause screen (its keyboard keys, depths 9 to 37 of `hammer_interf_instructions` frame 1, are hidden under the controller's buttons), the Loader's "click to start", the help dialog (controller block first) and the touch buttons (hidden). Buttons follow the controller (`padLayout`: Xbox, PlayStation, Nintendo, or generic with Xbox's buttons and Start / Select). They are the icons of three Figma Community sheets (CC BY 4.0, credited in the help dialog), cleaned by `tools/build-pad-icons.ts` from `assets-src/pad-icons/` (README there) and drawn in each screen's colors; a button with no icon is drawn by `PadGlyphs.ts` in their style (R1, and since G.4 L2, the stick presses and each D-pad arm). A notice shows when a player's controller is plugged in or unplugged; unplugging one during a game pauses it (`GameSession.requestPause`, which waits for the end of a level change). Tested in `tests/gamepad.test.ts`. No give-up (Ctrl+Shift+K) on the controller.
- Own keys and buttons (G.4, port addition): the settings page's "Touches et manette" row opens a controls page (`Shell.drawControls`), after the SWF's key setup screen that no code attaches (`#910`: the five moves with a key each, `labLeft` `labRight` `labJump` `labDown` `labFire1`, and a second frame "Appuyez sur la touche souhaitée" / "[ ECHAP pour annuler ]"). Each move has two keyboard slots (the defaults: the original's keys first, the port's W A S D / Z Q S D and X J second) and a controller slot. A slot waits for a key (Escape cancels) or a button (Start cancels; a click cancels too); the key or button leaves any other move. The game's keys (P, Escape, M, E, C, O) and buttons (Y, the bumpers, Start, Back) are refused with a note; a move's buttons are A, B, X, the triggers, the stick presses and the D-pad, which the left stick follows (so taking up off the jump stops the stick's up jumping too). `src/engine/Bindings.ts` holds the model, saved in `localStorage` (`hammerfenix_controls_v1`, checked on load). `InputController.setMoveKeys` puts the keys on every player whose mode gives none (every solo game; the co-op sides keep the mode's keys) and the buttons on every controller (`PadManager.moves`). The menus keep their fixed keys and buttons, and replays are unchanged (they record actions). The help dialog's move rows follow the bindings (`src/ui/HelpKeys.ts`). Not followed: the pause screen's keys (the SWF's own art) and the Learning mode's texts (the lang files) still name the original's keys. Found on the way: AZERTY's M (QWERTY's semicolon key) did not switch the music, as `flashKeyCode` only read letters on the QWERTY letter keys; a letter now counts wherever the layout puts it, as Flash's key codes did. Tested in `tests/bindings.test.ts`.
- World map (2C.4, `GameMode.onMap`): C (`fl_map`, on) pauses the game under `hammer_map`: the sector name, the pointer at the main world's level (`getMapY`) and the pit down to it, then an icon (`hammer_interf_mapIcon`, frame = `Data.EVENT_*`) per event. C or P closes it; C on the pause screen closes it too. Events (`registerMapEvent`, main world only, at `dimensions[0]`'s level): a portal's exit with "N. name" of the target level (`usePortal`; "undefined" for a target with no name, as AS2 writes it, e.g. 72 > deepnight 18), the return to the main world (`onRestore`), a death (`onResurrect`) and an extend (`executeExtend`); `EVENT_TIME` is the boss rush's (4.5, "Boss rush (4.5)"). Kept from the original: its filter of return trips reads `mapEvents`, where the travels never go, so it never applies; a level with n events gets its row of icons n times, stacked. Differences: also on the controller's L1. The pit has its `OVERLAY` blend since 2C.6. Not compared in Ruffle. Tested in `tests/map.test.ts`.
- Disguises (2C.3, `GameMode.getControls`): each press changes the player's head to the next one whose quest family the profile has (109 afro, 110 cerbère, 111 piou, 112 mario, 113 Tuberculoz cape), then back to the normal head. Read every tick, also in pause, as the original does; `fl_disguise` is on (only the boss rush, soccer and co-op modes turn it off). Deviation: the key is E, not the original's D, which moves right with WASD and ZQSD here; the quest texts still say "D". It is in the recorded action mask. Named in the help dialog; the original's pause screen does not name it. Tested in `tests/disguise.test.ts`.
- Offline play (5.3, port addition): the build's service worker (`tools/vite-plugin-offline.ts`) caches every built file and serves them cache first; the cache name is a hash of the files. Not in the dev server.
- Rendering (5.2): the page draws the stage only after a logic tick (`FixedGameLoop.stepCount`), as nothing in the game changes between ticks; site screens, their fade and a stopped loop draw every frame. Flash drew at the movie's 40 Hz. Each tick runs the clip steps due before it, then the logic (2C.7): Flash advanced the playing clips, then ran the game's main, then drew, so a frame script's `gotoAndPlay` shows its target (the shield's frame 19).
- Sound (5.1): `src/engine/Audio.ts` ports `SoundManager` from Motion Twin's `mtypes` library (`lib/SoundManager.mt`, github.com/motion-twin/mtypes, not in this repo) and the Loader's music `Sound` objects. A channel (`Data.CHAN_*`) is only a volume: sounds on it overlap, as Flash's `Sound.start` never stops the instance already playing (checked in Ruffle's `avm1/globals/sound.rs`). At most 32 sounds play at once, new ones are dropped (Ruffle's `AudioManager.MAX_SOUNDS`). Volumes are the original's for the site's settings (`$volume=100`, `$sound=1`, `$music=1` in the archived `try.html` and `soccer.html`): player, bomb, item and field sounds 50, enemies and interface 40, music 33 (16 paused, 0 muted with M). `Mode.playMusicAt` restarts a track even when it is already playing. Not ported: `SoundManager.fade` and `loop` (unused by the game, except the silent `sound_kick` loop when the music is off). Port additions: the page's sound switch, the pause of a hidden tab, and the files fetched at start and decoded on the first click or key (Flash had the sounds in the SWF, and the Loader downloaded the musics before the game). Tested in `tests/audio.test.ts`.

**Modes and the manager (4.0).** As in the original, each game is a new mode object: `GameSession.startGame` destroys the previous mode, resets what the `GameManager` holds (seed, game log, score key, sound channels, Loader) and starts the new one (`startGameMode`: `init()`), so nothing has to be reset by hand between games. `GameMode` holds the game (worlds, lists, players, HUD, views, pause, map, darkness, music state) on its own clip (`mc`, inside the session's `gameRoot`, the Loader's `game` clip), and is what entities and scripts see as `game` (`IGameContext`). A mode overrides the same functions as its original: `init`, `initWorld` (`addWorld` per level set), `initGame`, `initInterface`, `initPlayer`, `addLevelItems`, `attachBad`, `goto`, `startLevel`, `nextLevel`, `isBossLevel`, `onLevelReady`, `onLevelClear`, `onKillBad`, `onExplode`, `onEndOfSet`, `onGameOver`, `saveScore`, `onHurryUp`, `resetHurry`, `getDebugControls`, `main`. Port glue: the level sets load ahead of the game (`GameSession.loadSets`), since `addWorld` cannot wait for a file; the session picks the mode (`createMode`, `GameManager.startDefaultGame`); the mode tells the page through the session (`onLevelChange`, `onStateChange`, `gameOver`). Deviations: the previous mode is destroyed before the new one starts (the original's `transition` does it after `init`; here each game was a new page), so that its entities' destruction draws nothing from the new game's seeded numbers; and `Adventure` plays the session's current set (the set picker). One order now follows the original: `Adventure.goto` clears the perfect order before `GameMode.goto`'s lock check, not after (no effect in play: nothing calls `goto` while the game is locked). Tested in `tests/modes.test.ts`; the replay snapshots did not move.

**Co-op mode (4.2, G.3).** The site's `$mode` `multicoop` (`GameSession.isMultiCoop`). What the port follows:

- `MultiCoop` extends `Adventure`: its player is destroyed and two are inserted at cases (5, -2) and (14, -2), Igor on the arrows and Enter, Sandy (skin 2, `HEAD_SANDY`, `BASE_COLORS[1]`) on R, F, D, G and A. Each has half the lives, rounded up. No bullet time, no disguise; mirror and nightmare come from `mirrormulti` and `nightmaremulti` only.
- The game is over as soon as one player has no life left (`Player.killPlayer`), even if the other has some. With `lifesharing` a player with no life takes one from the other, while the other has a spare one.
- `GameInterface.initMulti` (frame 2 of `hammer_interf_game`): a score, lives (12 px apart, player 2's leftwards from x 300) and extend letters each. Frame 2 has no `level` field, so this mode shows no level number, as the original.
- `onPause`: frame 3 of the instructions, with both players' keys; it draws a second tip after `GameMode.onPause`'s, as the original.
- `saveScore` sends -1 as the score, the items, and each player's score in `$data` (`$s0`, `$s1`). The results screen shows both scores.
- `Adventure`'s Ctrl+Shift+M (start the co-op from the dev keys) is still not ported.

Guess: co-op games count for the quests and the fridge. The guide says items are won "dans le mode Aventure"; this mode is the Adventure for two and sends `$item2` as it does, while `TimeAttack.saveScore` sends null. The menu entry is locked until quest 67 ("Sandy commence l'aventure !", `give mode="multicoop"`). Names: "Multi Coopératif" (quest 67's text), "Two Players", "Cooperativo".

Not ported: `entity.WalkingBomb` (`bombcontrol`: one player, whose bombs walk with Page Up and Page Down). With the option the mode has one player on the arrows, Enter and Ctrl, as the original, but the bombs stay still.

Port addition (G.3), `src/game/gui/JoinScreen.ts`: a game the menu starts first asks each player for their device (`GameMode.askJoin`, from `GameSession`'s start). The game pauses on the first tick its controls are free, under frame 3 of the instructions: player 1, then player 2, presses a key of a keyboard side (the keys `initGame` gave a player) or a button of a controller. The row shows the keys chosen (moved to the player's row) or the controller's buttons. A player on a controller has no keys (`InputController.setPlayerDevices`, `PadManager.assign`); the screen closes half a second after the last choice, once everything is let go. If a chosen controller is unplugged the screen comes back for that player (`lostPlayers`), who plugs it back in and presses it, or presses another free device. The pause key does nothing meanwhile. Games started otherwise (debug toolbar, recordings, replays, tests) are not asked: they keep the original's keys and the controllers in connection order (G.2), so replays are unchanged. Not compared in Ruffle (it cannot start this mode); not tried with real controllers.

**Time Attack modes (4.1, 4.3).** The site's `$mode` `timeattack` and `multitime` (`GameSession.isTimeAttack`, `isMultiTime`). What the port follows:

- `TimeAttack` extends `Adventure` and replaces its world with the set `timeAttack` (`xml_time`); `TimeAttackMulti` extends it with the set `multiTime`. The run is the `$options` level set choice (`set_ta_N`, `set_mta_N`; without one the original stops with "unknown run ID", `GameSession.fatal`, which throws here) and starts on level 9 N. A run ends on the first empty level (`SetManager.isEmptyLevel`): run 0 is levels 0 to 5 in both sets, run 1 levels 9 to 14 (`timeAttack`) or 9 to 12 (`multiTime`); run 2 has no levels in either set (no quest gives it; the port then shows level 0 with no countdown, where the original would read a level that does not exist).
- Three lives per player, no score (`getScore` and `getScoreHidden` set to null), no level items (`addLevelItems` is empty, so no extend letter, special or score item), no super item (`perfectOrder` set to null at the level's end), no hurry up, no bullet time, no mirror, no nightmare. `fl_static`: walkers start to the right and flyers to the left, with no random draw. The original's walkers would look at their side of the screen, but `Walker.init` runs before `initBad` places them, while `x` is still 0, so all go right. The Tornade boost is skipped by `Player` when the mode is `$time` only, so it applies in the two-player version (`$timeMulti`).
- The chrono is real time (`Std.getTimer`, `GameSession.getTimer`), read once per frame; it stops while the game is locked (level change, pause, the dimension change) and each crystal takes 1 to 10 seconds off it (`Data.getCrystalTime`, by combo), never below 0, with a "-N sec" pop per player. A 3.5 s countdown (`hammer_interf_starter`: nothing, then 3, 2, 1) locks the first level, then "TIME ATTACK !" (static 20) starts the chrono, from the frame before (so it reads 31 ms on the first frame). An alert marks each new minute ("1 MINUTE", "2 MINUTES", statics 18 and 19). On each next level the previous level's time slides in at the bottom left (`hammer_interf_time`). The level name banner is removed.
- The time sent (`saveScore`, the score with the run id, no items, no data) is the sum of the level times, each taken when leaving a level (`goto`, from the previous frame's timer). Leaving the run's last level for the empty one ends the game before that level's time is added, so the last level is not counted, as in the original. A game over sends 3,599,999 ms (`INFINITY`, 59" 59' 999). A level time is negative when crystals took off more than the level took.
- `GameInterface.initTime` (frame 3 of `hammer_interf_game`): the chrono in the middle (`print`, formatted `MM" SS' mmm` as in UTC+1, like `Chrono.formatTime`), lives at both ends (from x 8 and x 386, 15 px apart; `fl_multi` stays off, so player 2's are spaced as player 1's), no score, no level number (frame 3 has no `level` field), no extend letters. The original changes the static `BASE_X`, `BASE_X_RIGHT` and `BASE_WIDTH`; the port keeps them per HUD.
- `TimeAttackMulti`: Igor and Sandy (skin 2, `HEAD_SANDY`, `BASE_COLORS[1]`; not her name or her dark color) on the level's start column and its mirror (`LEVEL_WIDTH - px`: on column 10 of level 0, the same column), on the arrows and Enter, and Z, S, Q, D and A. Its pause screen is `GameMode`'s one-player frame (no `onPause` of its own). As in every mode, a player with no life left ends the game (`Player.killPlayer`).

Port additions: the two-player version, started from the menu, asks each player for their device (G.3) before the countdown, which waits for it (`GameMode.canJoin`, `joinLocked`). The site kept a ranking of all players (`scores_timeattack.html`: position, player, time as `0' 06" 597`); with no server the profile keeps the player's best time per mode and run (`ProfileData.times`, in `hammerfenix_profile_v1`, a field older saves lack). The menu shows the chosen mode's best time under its text, and a Time Attack game's results page its time in the site's format (milliseconds padded, which the site did not do) with "Nouveau record !" or the best time; a lost game shows the game over picture and no time. Only games the menu starts set a best time. Time Attack games count for no quest (`saveScore` sends no items).

Guesses: no quest gives `multitime` or a `set_mta_*` option, and no quest gives `set_ta_1` or `set_ta_2`. The menu unlocks the two-player version once the profile has both the Time Attack (quest 73) and the co-op (quest 67) (`Profile.hasMode`), on run 0, and plays the first Time Attack run the profile has (run 0, from quest 73), so it shows no run choice. The maintainer kept these choices and the best times (2026-11-11). Lag: on a machine that cannot keep up, the game slows down while the chrono keeps real time, in both: the original caps `Timer.tmod` at 2.8 (below about 11 fps), the port's loop catches up at most 0.1 s per drawn frame (below 10 fps).

Not compared in Ruffle (it cannot start these modes); read from the code. Tested in `tests/timeattack.test.ts` and two replays (`tests/replays/timeattack.json`, `multitime.json`), and seen in the browser: the menu cards, the countdown, the chrono, a level change, the results page, and the join screen before the two-player countdown.

**SoccerFest (4.4).** The site's `$mode` `soccer` (`GameSession.isSoccer`). What the port follows:

(6): a click (`pauseMC.onRelease`, here `GameMode.pauseRelease`, from any click on the game) or P closes it, and "Préparez-vous..." (21) shows the first time. ## Quests and profile (3.2a research)

The original client never runs quests: the hammerfest.fr server counted the items each game sent, checked `xml/quests.xml` and answered the next start query with `$families` (`Loader.mt`). Its code was never released. The port rebuilds it in `src/game/Quests.ts` (rules) and `src/game/Profile.ts` (save). Sources: `GameManager.mt`, `GameParameters.mt`, `mode/QuestBrowser.mt`, `xml/quests.xml` and `xml/items`, the site guide (`guide.html` FR/EN/ES), the archived public profiles (`user_*.html`), and hamm4all.net (its API: `/api/v1/quests`, `/api/v1/families`, `/api/v1/items`).

**Settled from evidence:**

- **Item counts add up over all games.** Guide section 6: a quest "consiste à accumuler une série d'objets précis", and the fridge keeps "sa collection". Only the Adventure mode counts (guide section 4: items "sont acquis au cours du jeu dans le mode Aventure").
- **Quests are checked at the end of a game**, by the server, from the items the game sent (`$item2` of a game over, or the picks sent to `endGame.html`). The rewards apply "de manière permanente pour vos prochaines parties" (guide section 6), so never during a game. The results page had a quest progress table (`table.result`, `.statusCompleted` in green `#51cc15`).
- **Quest status:** the profiles list "Quêtes completées" and "Quêtes en cours" (in progress: started, not done), each in quest id order, and "Aucune! Il va falloir jouer plus!" when none is in progress.
- **Rewards** (`QuestBrowser.mt` lists all but `log`; the texts are the quests' `Lang` descriptions and hamm4all): `family` adds or removes an item family (families 100 to 113 are powers read by `Player` and `GameMode`, 5000 to 5099 world keys); `option` unlocks a game option (3.3); `mode` unlocks a game mode (Phase 4); `tokens` gives N free games (quests 32 to 34, "Vous avez gagné 5 parties supplémentaires"); `bank` raises the games each shop purchase gives (quest 35, "Vos appels dans la boutique vous rapporteront dorénavant plus de flocons"). `log` is only on quest 74 ("Maître des Bombes") and has no known effect.
- **Fridge:** an item shows once found `unlock` times, an attribute of `xml/items` (`<item ... unlock="1"/>`), 10 when absent. Guide section 4: "vous devez avoir trouvé au moins 10 fois un objet"; hamm4all uses the same values. 353 items (the profiles' "N objets sur 353").
- **No-site families:** `GameManager` uses `0,7,1000,18` ("using sysfam") for the tutorial and when the game runs with no site. In dev mode (the set `xml_dev` is present) it uses `0,7,1000,1001,1002,1` to `19` instead; `game.swf` embeds `xml_dev`, so the Ruffle side-by-side runs with those (2B.3). The port uses it for games the menu does not start (debug toolbar), and replays store their families (`Replay.families`; the first 6 replays were recorded with 0-2 and 1000-1002 and keep them).

**Guesses (no direct evidence):**

- **Starting families of a new player:** `0, 7, 18, 1000, 1020, 1024, 1028`. 7 and 18 are in the system set and removed by quests 2 and 35, but no quest gives them. 1020 (ice keys), 1024 (game pads) and 1028 (Sandy's kit) hold items with a rarity above 0, no quest gives them, and archived profiles completed "Sandy commence l'aventure !" (1028) and had "Meilleur joueur" (1024) in progress, so the server gave them. 1019, 1027 and 1029 only hold rarity 0 items (placed by scripts or events), so they make no difference and are left out.
- Quests do not use up their items (the fridge keeps counting, and several quests share items).
- Quests are checked in id order, once each; a quest's `give` and `remove` entries apply in document order.
- The end of the set (`endGame.html`) counts its picks like a game over.
- Games marked illegal (`$!` in the history) still count: what the server did with them is unknown.
- `tokens` and `bank` are kept in the profile but do nothing: the port has no game cost and no shop.

**Built (3.2b to 3.2d):** the profile (items, quests, families, options, modes, tokens, bank, games) is saved in `localStorage` under `hammerfenix_profile_v1`, encoded with `PersistCodec` and its CRC; a damaged save starts a new profile. Games started from the menu send the profile's families (`GameSession.setParameters`), and only those Adventure games are recorded (`GameSession.siteMode`). The menu has the site's "Quêtes" and "Réfrigérateur" tabs (`icon_quests`, `icon_inventory`): the quest screen lists quests done and in progress with their items ("found / needed") and, once done, the description; the fridge shows the 353 items in `items.xml` order, 60 per page, with their count, family and the site's `a.gif` for an item not in it yet. The results screen adds the quests completed and the new fridge items. The options unlocked are offered on the mode menu (3.3, see "Game options"). Tested in `tests/quests.test.ts`.

## Audit 1.6: session, bombs, shots, items

`GameSession.ts` (since 4.0 `mode/GameMode.ts` and `mode/Adventure.ts`) against `mode/GameMode.mt` and `mode/Adventure.mt`, plus `Bomb.ts`, `Shoot.ts` and `Item.ts`, 2026-11-04.

### Fixed

- Level flow follows the original chain: `goto` (players keep their x and fall from above) → IA parse (17 frames) → `onDataReady` (scroll starts, script compiles) → scroll (40 frames) → `onLevelReady` → `initLevel` → `startLevel`, all inside the world update, before the level script runs. A new game is locked until its first level is parsed (17 frames), as the original's `Mode` constructor locks it.
- The level script compiles and runs its first cycle when the level is read; enemies and items inserted at level start run on the next script update.
- Levels are marked visited when left, not when entered; level data (tiles changed by scripts) persists for the whole game.
- Hurry-up is reset only on unvisited levels, recomputes `diffFactor` from spare lives and nightmare mode, and switches the music to the hurry track and back.
- The fire ball of the second hurry-up starts as a harmless summon at anger 0 (it was instantly lethal at anger 1); later ones get `round(huTimer / AUTO_ANGER)` anger.
- Clearing a level removes the extend letters on screen; boss levels never clear by themselves; `onKillBad` no longer re-checks the clear.
- Main loop order: level script, HUD, portals, effects, hurry-up, entities, then level clear, floating portal, shake, exit arrow, nightmare anger.
- Boss levels (30, 40, ..., 100, 101) show the warning; `globalActives[94]` adds a second score item; extends are only inserted when the level has special slots.
- Portals: the dimension switch requires a cleared level, resets the players (temporary effects, weapon, controls), places them at the arrival portal (`getPortalEntrance`), knocks late players, and handles the floating portal's pull-in. A new game always starts in the main world.
- `getClose` included dead entities in the original; the port filtered them out.
- Shake: offsets use the original's integer draws, and the power resets when the shake ends.
- Bombs: no invented "already exploded" guards (only `Green` has one), `duplicate()` no longer sets owner and parent, red bomb and mine no longer clear `fl_stable`, the mine calls `blinkLife()`.
- Shots: rewritten from the original. Speeds, cooldowns (2 s for the player's arrow, fire ball and pearl), offsets and hit rules were invented: the player's fire ball and pearl go through enemies, pips and zests do not disappear on hit, a missed ball goes back to a random Fraise.
- World keys from quest families 5000-5099; `setBaseAnims` ported.
- `FxManager` (2C.2): `attachShine` draws its flip with `Std.random(2)`, and `dust` was rewritten from the original: 7 clips (not 6), `Std.random(50)+50*(±1)` as x scale (the sign applies to the 50 only), y scale 10 to 89, a start frame 5 to 9, and the draws happen even when the fx is not attached (the game is locked). Its low detail skip is in since 2C.5. The 4 replays with dust changed their random sequence.
- `Mode.updateConstants` (2C.7): `cycle` no longer counts while the game is locked (level scrolls, pause), as in the original; it times the temporary item effects (`SpecialManager.tempList`) and the player's recent kicks. No replay changed.

### Open

## Audit 1.7: level script, world and view

`levels/ScriptRunner.ts` against `levels/ScriptEngine.mt`, `levels/LevelWorld.ts` against `SetManager.mt` and `GameMechanics.mt`, `levels/LevelView.ts` against `View.mt`, 2026-11-04.

### Fixed

- Script tree: Flash's `removeNode()` leaves `nextSibling` null, so `runScript` stops at the first trigger removed in a cycle; the triggers after it run on the next cycle. The port ran them all at once (checked in Ruffle's XML code).
- A trigger nested in another one is moved to the end of the script (`appendChild`): the events after it in its parent are skipped (deepnight 141 in ninja mode never shows message 163), and a repeating parent adds it only once (deepnight 184).
- Level start order (`ViewManager.onDataReady`): the view is created and `$attach` set before the compile. A level shown without a transition (new game, level picker, warp start) is ready before its script compiles, so its enemies appear on the first cycle; after a level change the script compiles when the scroll starts and the enemies appear when it ends. Players are placed before the compile.
- The script only runs while the world is unlocked (`world.lock` in `goto`, pause and `suspend`; `unlock` in `startLevel`); the level clear is only checked then.
- `GameMechanics.suspend`: the script left is saved into the level data when a dimension is left, so coming back runs what was left of it.
